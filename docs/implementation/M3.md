# M3 — Durable Task（进行中）

当前完成了 Temporal SDK 与 Worker 中断恢复探针、Task start 的事务命令、Outbox 租约派发基础，以及 Task 事件的分页/SSE 读取。**M3 尚未验收**：正式 TaskWorkflow 与 Worker 主循环未接通，用户任务不能启动。探针故意不修改 AYRA Task、Run 或 Artifact；它只验证运行环境与 Temporal 的持久化执行能力。

## 已验证

- `@temporalio/client`、`@temporalio/worker`、`@temporalio/workflow` 固定同一版本 `1.24.0`，Worker 使用 Node.js 原生桥接。
- `pnpm test:temporal` 连接本机 `ayra-development` 命名空间，创建唯一 Workflow ID 和 Task Queue；等 Workflow 进入等待状态后，向第一个 Worker 发送 `SIGKILL`，启动第二个 Worker，读取恢复后的状态，发送 signal，验证原 Workflow ID 返回预期结果。
- 探针代码位于 `apps/worker/src/durability-probe.workflow.ts` 与 `apps/worker/scripts/`，仅用于验证。正式 Worker 入口仍不接收用户任务。
- 已提供授权的 `GET /v1/tasks/:id/events?afterVersion=N&limit=50` 分页事件投影，直接读取同一事务写入的 Task Outbox 事件。游标使用 Task 的 canonical version；跨 Workspace 和暂停成员不可读取，应用角色没有直接读取 Outbox 表的权限。断线后可从 `nextAfterVersion` 续读。
- 数据库函数 `ayra.start_task_attempt(task_id, expected_version)` 在单一事务中校验 Owner 与 Draft 版本、创建新 Run、将 Task 置为 QUEUED 并通过触发器写入 Audit/Outbox。重复调用只返回冲突，不会再创建 Run；跨租户及暂停成员得到 NOT_FOUND。该命令尚未开放用户 API，避免在 Temporal 派发尚未接通时产生永远排队的任务。
- Outbox start 事件加入 30 秒可重领租约、attempt 计数与 token 绑定的确认函数。集成测试模拟 Worker 在确认前中断，验证到期重领、旧 token 不能确认、新 token 能确认。Worker 的单批派发器会重新检查 Task/Run canonical 绑定，使用确定性 `ayra-run-{runId}` Workflow ID，并把 Temporal 的重复启动错误当作已交付。派发器尚未接入正式 Worker 主循环。
- `GET /v1/tasks/:id/events/stream` 已提供 SSE：首连和断线重连使用 Task version 游标（也接受 `Last-Event-ID`），长连接每次轮询重新验证 JWT、会话和 Workspace 权限。HTTP 集成测试验证事件重放与成员暂停后流关闭；它仍只是事件 projection，不承担 Workflow 生命周期。
- `taskWorkflow(runId)` 已按 load → Understand → Plan → Execute → Verify → Complete 的 Activity 边界编排；外部执行 Activity 最大尝试次数为 1，避免不明结果的写入被盲目重试。使用**测试专用的可控 Activities**，真实 Temporal 测试验证 pause、Worker `SIGKILL` 后 resume/complete，以及 cancel。AgentRuntime、Artifact canonicalization 与 Approval wait 仍未实现，不能据此认定用户任务可运行。
- Worker 数据库 Activity adapter 已加入：按 Run ID 读取 QUEUED Task，受数据库状态机保护地写入阶段与 Run 状态；完成前必须调用注入的 Artifact canonicalizer。集成测试验证非法跨阶段更新回滚、逐阶段事务/事件与重复完成幂等。AgentRuntime 和 Artifact canonicalizer 目前只有测试替身，尚无生产实现。
- 端到端 M3 集成测试在真实 PostgreSQL + Temporal 上执行：Task start 事务写 Outbox，单批派发器启动 Workflow，客户端断开并强制杀掉 Worker 后，新 Worker 恢复同一 Workflow，最终 Task/Run canonical 状态为 COMPLETED、阶段事件顺序与数量正确。测试 Worker 明确使用可控 Agent；因此它验证持久化链路，**不验证真实 AI 业务结果或发布就绪**。
- 结果 Artifact 已接入本地 S3-compatible 存储：确定性 Workspace/Task/Run key、SHA-256 校验、条件写入和重试时 HEAD 核对；数据库用 Run 级唯一索引与校验函数注册元数据。端到端测试读取对象验证内容，并对同一 Run 重复 canonicalize，确认只产生一个 Artifact。当前测试 Worker 仍使用可控 Agent；生产对象存储凭据、Artifact 内容授权读取与清理策略待实现。

## 后续验收条件

- 将 `TaskWorkflow(runId)` 接到正式 Worker：实现 AgentRuntime、Artifact canonicalization、Approval wait，并将 Outbox 派发器接入主循环；在真实 Task 上验证确定性 Workflow ID 与重复投递去重。
- 实现用户授权的 start/cancel/pause/resume，Task canonical state、Run 状态与事件流均由数据库事务维护；Workflow 不能替代 canonical state。
- 在真实 Task Workflow 上验证客户端断开不影响任务，以及 SSE 断线续读与 canonical 状态一致。
- 使用正式 AgentRuntime/Artifact 路径做 Worker `SIGKILL` 恢复，并验证重复 Outbox 不创建第二个 Run/Workflow、发布配置与权限边界。

`pnpm test:temporal` 需要先运行 `pnpm infra:up` 并具备 `.env.local` 中的 Temporal 地址/命名空间。通过探针并不表示 M3 或产品发布完成。
