# V1.0.4 弹窗层级审查

## 已复现的根因

确认框使用固定 z-index 6000，普通表单使用 5000。收银 Confirm 等待 API 操作，而 API 先通过 askReason 打开普通原因表单，形成新表单位于旧确认框之后、旧框持续“处理中”的阻塞。浏览器回归在修复前真实点击 textarea 超时，明确报告旧确认文字 intercepts pointer events。

## 审查范围及修复

- 检查全部 renderer 的 Modal/Confirm 使用点（68 行引用）及所有 fixed 全屏遮罩、dialog/alertdialog。确认所有标准业务弹窗共用 ui.tsx。
- 标准弹窗改为打开顺序栈，布局提交时同步层级。类型 dialog/alertdialog 不决定视觉优先级；只有顶层可交互，底层 inert。Escape/Tab 与视觉顺序一致，关闭后恢复上一层焦点。
- 取消原因输入按 AbortError 处理，不误报提交失败；确认框解除忙碌状态后可再次操作。
- 7 处独立弹窗迁移到同一 Portal 和焦点/层级栈：房态技师今日安排、预订详情、巡房、巡房异常；收银收款码、结账明细；钟房呼叫技师。保留原有表单、尺寸及忙碌保护。
- 房态右键菜单保留在业务弹窗下方；非模态房间预警和更新通知保持非模态，不作为业务表单抢占焦点。收银主面板属于工作区，保留其基础层级。

## 受益业务

原因输入调用点逐项核对：期初会员权益、会员权益调整、退单、赠送、改价、结束服务、优惠、反结账、取消订单、充值冲销、退还押金。它们共用同一原因表单与弹窗栈。会员详情/编辑、库存、审批、营销以及平台门店维护的嵌套弹窗也沿用该栈，未逐项追加 z-index 补丁。
